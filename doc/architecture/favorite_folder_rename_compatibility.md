The helper reuses the existing name validator, input presentation, task ownership and manager/repository transaction; no forwarding entry or second persistence implementation is added.

Validation reads the original manager folder names. After the user accepts a valid name, actual AppDataOperations admission verifies manager cache identity, connection generation and App.dataPath before calling rename. Original-host cancellation or page removal does not discard an already accepted queued write, while database replacement retires that write before it reaches the new connection. The helper records a name only after successful persistence or an explicit PersistenceFailure(committed). Unknown outcomes remain unconfirmed, with no automatic replay; notCommitted permits explicit retry. Publication waits for both input presentation and its last accepted confirmation, including user dismissal while saving. Only the valid original page receives the resulting name. This ordering allows FavoritesPage to replace its keyed local child after the input has finished using the old context. Publication errors retain committed status, original cause and stack, and cannot replay the rename.
