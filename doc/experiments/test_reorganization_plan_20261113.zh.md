## 1. 目标和范围

本轮目标是让测试职责清楚、夹具集中、关键回归有实际执行保障，并减少重复代码、无效断言和等待成本。文件数、用例数和行数用于观察变化，不设“删除一半”等配额。

整理范围覆盖根 `test/`、被根测试复用的包内测试、自管原生模块测试、CI 脚本测试、构建与设备探针、相关工作流和开发文档。不能仅整理 Dart 文件而遗漏独立运行的原生或工具测试。

| 范围 | 本轮处理方式 |
| --- | --- |
| `test/features/`、`test/foundation/`、`test/components/`、`test/app_runtime/`、`test/routing/` 等 | 全部盘点；按行为和资源需求整理、合并、拆分或核实删除 |
| `test/support/`、`test/fixtures/` | 整理辅助函数、领域夹具、子进程探针和样本引用；保留样本来源与许可证 |
| `.github/scripts/tests/`、工作流 | 检查行为保障、脆弱文本断言、测试发现、触发条件和结果汇总 |
| `packages/photo_view`、`share_plus`、`venera_native`、`venera_saf`、`rhttp` 等包内测试 | 区分上游测试、应用入口包装和本地补丁回归，核实直接及间接执行入口 |
| `apple/Tests/`、`windows/tests/`、`test/native/` | 登记 Swift、C++、Kotlin 的编译和运行方式，补齐实际执行缺口 |
| `tool/harmonyos/`、`tool/saf_provider_probe/`、`tool/code_audit/` 及诊断探针 | 区分自动回归、兼容性构建、自检与手动设备验收；分别记录结果 |

实施提交以测试、测试基础设施和文档为主。若发现业务缺陷，单独记录并保留有效回归，不将业务修复混入测试整理提交。SDK、依赖升级、数据库格式、用户功能、历史提交和发布资产不作为本轮整理对象。#163、#81、#123 的新增功能工作继续搁置；对应现有行为的有效测试仍按同一标准保留。

## 3. 分类与清单设计

分类使用独立维度，继续沿用业务目录。文件名含 `integration`、`native` 或 `legacy` 仅提供线索，不作为唯一分类依据。

| 维度 | 内容 |
| --- | --- |
| 被保护行为 | 业务入口、前置条件、操作、可观察结果、错误及收尾行为 |
| 测试层级 | 逻辑单元、组件、组件／业务集成、真实存储／传输、子进程、原生、设备验收 |
| 环境 | 支持的 OS、SDK／flavor、原生库、窗口能力、模拟器或设备、外部工具 |
| 风险 | 数据完整性、资源生命周期、发布约束、核心阅读／输入、普通界面 |
| 执行成本 | 实测耗时和所需准备；不因“原生”或“集成”标签直接判定为慢 |
| 执行归属 | 本地命令、CI job、触发条件、预期跳过原因、结果产物 |

清单分两部分：机器生成全部文件和实际运行结果；人工维护改动用例的行为对应及决策理由。不要手工复制所有动态测试名称，形成另一份难以同步的巨型清单。参数化用例的实际数量与完整名称从 machine 事件读取，静态正则扫描只用于发现候选。

执行配置拟使用轻量的 `test/suites.json`，通过目录规则和少量文件覆盖项记录套件、环境及例外。必要的清单校验／执行辅助脚本放在 `.github/scripts/`，使用明确的参数数组传递文件，保持测试失败的退出码；不引入另一套测试框架。原始 JSON、日志和覆盖率保存在 `build/test-audit/<commit>/<platform>/` 及 CI artifacts，仅提交稳定配置、摘要和决策记录。

配置必须检查全部跟踪测试的归属、未匹配文件、过期路径、非预期重复执行和合法入口包装。迁移期未分类的 Dart 测试仍进入现有全量执行；分类完成后未归属的新文件使清单检查失败，不能静默遗漏。普通、TV、不同平台及有意复用包内入口属于不同执行场景，应显式登记。

## 4. 保留、合并与删除标准

| 决策 | 必须具备的依据 |
| --- | --- |
| 保留 | 保护当前功能、兼容格式、独立故障模式或平台契约；能够说明失败时的用户或维护影响 |
| 抽取夹具 | 多处重复准备具有一致生命周期；抽取后每个用例仍有独立实例与资源收尾 |
| 拆分 | 同一文件包含不同业务职责、环境或资源需求；拆分后入口和行为对应可核对 |
| 合并／参数化 | 前置条件、入口、结果及收尾相同，仅输入数据不同；独立边界仍有可读的用例名称 |
| 改写断言 | 当前断言主要锁定代码文本、内部调用细节或格式，而真正约束可以通过结构或行为表达 |
| 删除 | 对应路径已移除或已证明重复／无效；确认没有独立边界，并记录保留的替代测试或当前代码证据 |

跨层级覆盖同一功能不自动视为重复。单元测试保护规则，组件测试保护控件接线，集成或子进程测试保护实际持久化与中断恢复；真实 ABI、句柄释放和进程崩溃测试不能被 mock 的“调用过一次”替代。

必须保留的关键回归包括：旧库／旧备份迁移、身份冲突、事务失败回滚、跨库原子性、同步竞争与中断恢复、下载续传与取消、归档损坏及路径边界、FFI 所有权和内存安全、过期页面／回调不能操作新会话、退出保存与窗口恢复、TV 输入和低内存、签名与发布产物来源核验。

例如 `favorites_manager_test.dart` 的旧库索引和重启保留用例仍对应生产兼容逻辑；`legacy_image_provider_cancellation_test.dart` 仍保护当前图片 provider 的取消与共享流释放。它们不能因名称带 `legacy` 被删。

每项合并或删除至少记录：旧文件与用例／参数组、保护的行为、处理理由、新文件与替代保障、适用平台、验证结果和批次 commit。未决候选继续保留；不把测试临时搬到不被发现的目录当成删除完成。

## 5. 辅助代码的目标组织

继续保留 `test/features/<feature>/`、`test/foundation/` 等业务目录。单模块共享的夹具放在该模块的 `support/`；跨模块复用放在根 `test/support/`。现有合适的辅助文件继续复用，不为统一外观机械搬迁。

| 辅助代码 | 目标 |
| --- | --- |
| 侧栏 pump、异步完成等待、错误原因展开 | 根 `test/support/` 的独立 UI 辅助文件，先解除广泛的测试文件依赖 |
| JS UI、归档和编辑器公共操作 | 按各自用途抽取，避免建立一个混入所有场景的万能 UI 夹具 |
| 阅读器会话、应用宿主和假图片准备 | `test/features/reader/support/`，按资源所有权提供明确创建与关闭方式 |
| 收藏／下载／同步的领域数据 | 优先复用现有夹具；各用例独立临时数据库、目录、端口和控制对象 |
| 原生库定位与能力准备 | 统一环境准备，区分“平台不适用”和“必需依赖未准备”；后者应失败 |
| 子进程崩溃／恢复探针 | 保留 `test/fixtures/*_probe.dart` 的真实进程入口，集中公共启动与结果读取 |
| AVIF、归档、旧库等样本 | 保留真实边界样本、摘要、来源和许可证；仅删引用已消失且无独立价值的样本 |

抽取时必须保留 MethodChannel、日志、单例／全局状态、计时器、数据库、请求和窗口 mock 的恢复顺序。异步等待应等待明确条件并有超时与错误传播；固定延迟是否可替换要逐项判断，不能把所有 `pump` 统一改成 `pumpAndSettle`。

## 6. 实施阶段与退出条件

阶段顺序为 **S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7**。S1 先解决执行保障，S6 在职责和成本清楚之后优化 CI。每个阶段可以包含多个小提交，但一次提交保持单一目的。

### S0：完整盘点与运行基线

- 对全部范围登记测试源、样本、自检、编译检查、直接及间接执行入口。
- 读取已有 CI 产物；缺少逐文件数据时，在正常 CI 验证中增加一次 machine 记录。分别记录准备、编译、测试、覆盖率和设备步骤，区分并发文件时长与 job 墙钟时间。
- 收集失败、跳过、原生依赖未就绪、临时目录与共享状态使用情况；文本相似度只产生审查候选，不自动删除。
- 建立模块行覆盖率及关键行为表。最近运行不足以计算稳定分位数时，报告样本量和原始耗时，不虚构 P95。

交付：基线摘要、文件执行清单、耗时排行、执行缺口列表和候选决策表。退出条件：所有跟踪测试源都有归属，所有未知项有明确待办，具备后续比较所需的可靠数据。

### S1：补齐平台入口与清单校验

- 逐项审查 75 处 Windows 条件：真实 Windows 行为进入 Windows 套件；仅因库定位或历史准备方式受限的用例，核实能否使用已准备的 Linux 库。
- 混合文件先保持原执行，必要时拆出平台组；不能仅用文件标签排除同文件中的通用用例。
- 将 Windows-only、Windows 原生及窗口生命周期套件纳入可靠执行入口；`test/**`、清单和相关辅助脚本变更必须能触发所需任务。
- 核实根 `test/native/` 的独立 Kotlin 回归及包内测试入口，将缺少运行保障的有效测试接入适用任务或明确设备步骤。
- 保留现有全量测试，新增清单完整性检查；所需原生库缺失应使适用任务失败。

交付：执行矩阵、清单校验、平台套件与触发条件修复。退出条件：所有自动化关键用例有适用环境入口，平台不适用与未执行状态可区分，不再依赖隐含的文件白名单。

### S2：抽取公共夹具与辅助函数

- 优先抽取侧栏辅助函数，再整理 JS UI、归档、编辑器、图片收藏数据构造。
- 逐组更新引用并运行消费者测试，核对异步收尾、错误传播和全局状态恢复。
- 为包内入口包装建立有说明的例外，确认没有因同时直接和间接执行而产生无意重复。
- 先搬移已有逻辑；夹具行为简化、等待策略改写放在后续独立提交。

交付：集中辅助代码及引用清理。退出条件：借用辅助函数的 `_test.dart` 相互导入归零，合法入口包装保留，消费者行为与资源收尾一致。

### S3：拆分阅读器大文件

对 `reader_exit_integration_test.dart` 建立原用例到目标职责的映射，优先复用已有同职责测试文件，缺少合适入口时再新增。

| 目标职责 | 应保留的保障 |
| --- | --- |
| 退出与宿主关闭 | 保存完成、窗口及方向恢复、失败收尾、应用最终关闭 |
| 菜单与手势生命周期 | 延迟 tap／长按、右键、过期回调、菜单锁、解锁与输入焦点 |
| 阅读进度与导航 | 七种模式、页码边界、章节身份、元数据替换和历史恢复 |
| 导出与图片操作 | 原始内容身份、页面替换、选择期间关闭与任务资源释放 |
| 设置与章节抽屉 | 原会话所有权、布局／模式变化、重复章节 ID 和过期操作 |

交付：按行为组织的阅读器套件、领域夹具、用例对应表。退出条件：原文件中的有效行为均有明确去向，Windows 组实际执行，普通／TV 相关回归通过。

### S4：逐模块核实重叠与精简

按下列顺序逐批处理，不一次改动所有模块：

| 批次 | 主要工作 | 核心保留项 |
| --- | --- | --- |
| 收藏 | 分离管理器、旧库迁移与 UI 所有权；共享目录和漫画构造；参数化相同规则输入 | ID／层级、排序、重命名、冲突、失败回滚、重启保留 |
| 本地漫画／下载 | 区分导入、归档、文件身份、下载状态和恢复；核实样本与夹具重叠 | 真实文件结果、取消／恢复、共享目录、坏包与原子提交 |
| 同步／备份 | 分离传输、导入结果、事务日志和宿主收尾；复用服务器与数据构造 | 竞争、上传失败、导入失败、进程崩溃、旧备份、双库恢复 |
| 漫画源运行时 | 区分解析／规则、脚本调用、安装事务和原生 JS 所有权 | 真实 ABI、取消、关闭、过期回调、事务恢复；不依赖第三方源站 |
| foundation／network／app_runtime | 按服务职责核实规则层与集成层重叠，统一环境准备 | 共享流、缓存、请求取消、资源释放、启动失败、无头进程 |
| 其余较小模块 | 清理已证实无效或重复的断言，保持单一行为和清楚入口 | 当前功能的独立边界与平台接线 |

每批按“候选 → 当前代码及消费者核查 → 保留／改写／合并／删除决策 → 验证 → 记录”执行。用于证明已失效回调、失败回滚和所有权边界的相似测试，必须比较具体故障模式后才决定。

交付：逐模块整理结果和决策记录。退出条件：每项合并、删除均可追溯，相关关键行为与覆盖率没有无法解释的下降。

### S5：脚本、原生和样本整理

- 将工作流的 job 依赖、权限、触发、产物要求和发布前置条件尽量改为结构断言；脚本的参数、成功／失败行为继续用实际执行或函数结果验证。
- YAML 解析不能依赖 CI 恰好预装的包；优先评估已有锁定能力。若确需新开发依赖，单独按来源、版本、许可证和安全规则处理，并注意 GitHub `on` 键的 YAML 解析语义。
- 保留 HAP／manifest／摘要、草稿与公开资产核验、旧格式兼容、签名和来源门禁；不能删掉文本断言后留下空白保障。
- 整理自管原生与包内测试的入口、样本和说明；ABI／ASan／UBSan、Swift 授权、分享所有权、Windows 启动等保障继续独立执行。
- 对探针、旧样本和辅助脚本检查源码、文档与工作流引用。找不到自动入口不等于废弃；先区分手动验收用途和失去用途。

交付：脚本行为与结构保障、包内／原生入口清单、样本去留依据。退出条件：当前契约继续被验证，样本来源可追溯，自动与手动证据没有混记。

### S6：CI 分层、分片与覆盖率汇总

- 将不需要原生构建的快速测试提早执行；原生库准备、sanitizer 和需要原生库的测试按依赖并行，所有必要结果仍进入总门禁。
- 根据 S0 数据先评估少量分片，按实际耗时和资源冲突平衡；不盲目增加并发，避免子进程、数据库及大图造成内存峰值和随机失败。
- 普通 Flutter 全量验证在迁移期及完成后继续覆盖 PR、主线与发布质量入口。优化首先使用夹具复用、消除无意重复和分片；关键慢测试不能仅移到手动或夜间运行。
- TV 使用真实 flavor 与原有编译参数；Windows、Android Provider、Apple、Rust 和鸿蒙继续保留各自环境与约束。
- LCOV 合并按规范化源码路径与行号合并命中，去重后计算分母；不能直接拼接报告让重复记录影响现有统计脚本。普通平台基线与 TV／其他变体报告分别说明。
- 汇总任务严格处理失败、取消和意外跳过；仅明确不适用的任务可跳过。测试筛选或清单错误必须失败。
- 调整 job 时保留现有 required checks 名称或用稳定总门禁兼容；若需要改变仓库保护配置，先完成可审查实现并明确所需管理员操作。

交付：有完整性校验的执行配置、分片和合并覆盖率、job 级耗时摘要。退出条件：旧全量套件的适用用例在新任务并集中均有执行，门禁没有被筛选或跳过削弱，性能与成本有可比较数据。

### S7：收尾与长期维护指南

- 汇总整理前后规模、夹具依赖、实际执行数量、预期／意外跳过、模块覆盖率和 CI 关键路径。
- 使用后续正常 CI 的至少三个同类样本比较耗时中位数，并记录 runner、缓存和准备差异；不为追求漂亮数据反复重跑全量。
- 将本地命令、环境准备、清单更新、平台入口及新增测试规则写入 `doc/development/` 的中英文指南，更新贡献指南和文档索引。
- 保留本轮基线和决策摘要，原始产物按现有 artifact 规则保存；逐项核实所有阶段退出条件。

交付：最终整理报告、维护指南和剩余设备验收事项。退出条件：本方案第 9 节的硬性条件全部满足，仍需设备的事项明确记录其实际状态。

## 8. 验证方式

每批验证采用项目指定 SDK 和锁文件。源码／测试重构提交遵循贡献指南的版本、结构、Python、Dart 分析、完整 Flutter 和 diff 检查；受影响文件及消费者的定向运行用于快速发现问题，不能代替批次必需的全量及平台结果。

| 改动类型 | 额外需要核实的内容 |
| --- | --- |
| 纯搬移／拆分 | 原测试行为映射、完整发现、消费者引用、平台归属 |
| 共享夹具 | 多消费者执行、资源独立、收尾顺序；对确有共享状态风险的组使用一次不同顺序验证 |
| 合并／删除 | 替代用例保护同一边界，关键断言存在；模块覆盖率及真实状态结果对照 |
| 异步／进程用例整理 | 超时、异常传播、实际子进程中断、恢复后的数据库及文件结果 |
| 工作流与筛选 | 未匹配、新文件、失效路径、重复分配、失败／取消／跳过传播、仅测试变更触发 |
| 分片与覆盖率 | 并集完整、重复执行解释、命中集合合并、统计分母与旧报告一致性 |
| 原生或平台入口 | 使用实际库和适用环境运行；设备步骤按既有验收要求记录 |

如果实现清单校验或报告合并工具，测试应针对遗漏、错误筛选、失败状态和错误覆盖率等真实风险；不为文档、机械搬移或每个简单辅助函数再增加镜像测试。

本轮方案文档只需检查文档链接、版本／结构、Python 脚本测试和 diff；不为制定方案重复运行约 23 分钟的 Flutter 全量 job。

## 11. 风险与回滚

| 风险 | 处理与回滚方式 |
| --- | --- |
| 抽取夹具改变全局状态或关闭时序 | 保留原收尾语义，验证所有消费者；定位后只撤回对应夹具批次 |
| 相似用例实际保护不同故障模式 | 合并前对比入口、身份、阶段、失败及收尾；依据记录恢复被删用例 |
| 分片遗漏新文件或混合平台组 | 清单完整性与执行并集校验；出现不明遗漏时恢复原全量入口 |
| 并发造成文件、端口、原生或内存冲突 | 先独立资源，再按测量限制并发；回退并发配置，保留有效测试 |
| 覆盖率合并美化了数字或重复分母 | 比较源码路径／行号命中集合；回退合并方案并保留分片原始报告 |
| 结构断言迁移漏掉发布顺序或来源要求 | 建立旧约束到新断言对应；缺少替代时保留原断言或撤回该批 |
| 平台任务需要设备或管理员能力 | 完成可审查代码与自动部分，记录具体待验收／配置事项，不将其写成通过 |

回滚使用普通的批次 revert，不重写历史、强推或修改已发布 tag／资产。实现只针对已核实文件和引用操作，不批量清空测试目录。正常产品开发继续前进时，基线比较需说明新增功能测试，不能把同期必要增长误记为整理失败。

## 12. 整理后的维护规则

- 新测试先说明独立保护的行为和实际执行入口，优先复用合适夹具；无需为每个函数机械建立一个文件。
- 新增平台或原生用例同时更新执行清单与环境准备。平台不适用可以明确跳过，所需依赖缺失应失败。
- 测试文件超过约 1,000 行时审查职责是否混杂；作为审查提醒，不设置机械的行数硬门禁。
- 多处重复且有一致资源生命周期时再抽取辅助代码，避免过度参数化或万能夹具使故障难以定位。
- 测试断言以输出、状态、文件／数据库结果和资源生命周期为主，文本断言仅用于确实需要稳定格式的契约。
- 保留真实兼容样本与来源信息；手动探针与自动回归标明用途，不能将未执行或编译成功误记为运行通过。
- 每次合并／删除附替代保障与验证记录；每个实施批次同步 changelog，并完成相关 CI 后再推进下一批。
