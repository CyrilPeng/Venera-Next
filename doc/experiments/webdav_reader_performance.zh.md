# WebDAV 阅读卡顿分阶段排查（#125）

## 现有证据与边界

反馈描述 Android 在分页、条漫、瀑布流加载下一张 1500×2400 图片时卡顿，下载到本地后仍然发生。它提示应检查共用图片管线，但不能据此认定是网络、解码、去混淆或某个阅读模式的根因。

2026-10-28 首次[请求核对版本与最小对照信息](https://github.com/CyrilPeng/Venera-Next/issues/125#issuecomment-6462490650)时，最新官方候选包为 `v1.18.2-rc.1+237`。作者随后[更正原版本为 `1.18.1-rc1`，并称最新 rc2 仍复现](https://github.com/CyrilPeng/Venera-Next/issues/125#issuecomment-6468429322)，补充荣耀 winRT、Android 16、JPG／PNG、200 KB 至 2 MB；又确认[下载后从本地入口阅读仍发生，快速翻回也会出现](https://github.com/CyrilPeng/Venera-Next/issues/125#issuecomment-6468655154)。录屏包含多种尺寸的壁纸测试图，复现集不能只覆盖原描述的 1500×2400。完整构建号、图片处理配置和 Android 帧耗时仍未核实；不再把机型、格式或本地入口对照列为尚未收到的信息。没有下载私人漫画、日志附件或备份。

目前没有 Android 设备连接，没有复现原报告的真机帧表现。开发侧已复现并修复下述缓存键兼容问题，但它尚未发布，也不能据此认定覆盖了所有模式的卡顿。#125 保持开放；#91 的发热耗电仍是单独的验收范围。

## 已复现的缓存键兼容问题（未发布）

`ComicImage` 与 Flutter `Image` 用 `ScrollAwareImageProvider` 避免在高速滚动时启动无用图片加载：已缓存或正在加载的图片应直接复用，其余图片才延迟。阅读器的 `ReaderDisplayImageProvider` 为了独立管理每个阅读会话的暂停、取消和收尾，不将显示代理自身放进全局 `ImageCache`，而由底层 `ReaderImageProvider` 共享缓存。原先代理返回自身作为 key，导致滚动策略查询不到底层 pending／decoded 缓存，即使图片已解码，仍可能等滚动减速后才显示。

最小修复让代理委托底层 provider 获取 key，不改变代理的会话归属、流转发和退出保护，也不重复缓存代理。冷图片仍按原策略延迟；没有增加缓存上限或解码并发、取消资源收尾、默认降低画质，也没有改网络或图片处理策略。

新增 `test/features/reader/scroll_aware_display_image_test.dart`，用合成 32×48 PNG／JPEG、真实 Flutter 图片缓存，以及确定性的滚动加载策略，隔离验证以下路径：

- 缓存预热后，直接 provider 是对照；显示代理必须同样显示，且字节读取与 decoder 创建均不增加、缓存只有一个底层条目。
- 已在加载中的图片可共享结果，不因快速滚动延迟其已经到达的画面。
- 未缓存图片在高速滚动期间不开始读取，减速后才加载。
- 缓存命中仍尊重阅读会话暂停，恢复后才向可见消费者交付；延迟期间移除控件不能启动迟到加载。

覆盖 Flutter `Image` 和生产 `ComicImage` 两条消费路径，共 12 项：修复前 8 项失败、4 项对照通过，修复后全部通过。测试确定的是缓存键与加载策略的功能缺陷，不测真实滚动速度、Android UI／raster 帧耗时或功耗。单页画廊的尺寸探针会直接订阅图片流，因此这项修复不能被扩大为分页、连续、瀑布流的所有卡顿均已定位。

连续／瀑布流的预加载目前主要预下载网络编码字节，本地文件跳过预下载，并不保证提前解码。该现状不是本轮已证明的第二个根因；先保留边界，待真机采样后再决定是否需要有界的局部预解码。v1.18.2-rc.2 安装包不包含本节修复，不能要求用户重复安装同一个候选版来验证它。

## 可复现宿主探针

`tool/reader_decode_probe.dart` 生成同一组彩色合成像素的 PNG 和 JPEG，默认尺寸 1500×2400。每种格式分别测试本地文件读取和已在内存中的编码字节，各预热一次、记录五次。

```powershell
flutter test --no-pub --reporter expanded tool/reader_decode_probe.dart
```

使用仓库指定的 Flutter 3.41.4。可通过 `--dart-define=READER_PROBE_RUNS=10` 调整次数，或使用 `READER_PROBE_WIDTH`、`READER_PROBE_HEIGHT` 指定合成图片尺寸。只在忽略的 `build/reader-decode-probe/run-*` 内生成测试文件，不访问用户数据或网络，不需要私人输入。

本地字节读取调用生产 `ReaderImageProvider.load`，在测试进程内临时关闭自定义图片处理，结束后恢复。后续使用 Flutter 的 `ImmutableBuffer`、`instantiateImageCodecWithSize` 和 `getNextFrame` 入口分阶段计时，核对读取字节与解码尺寸并释放图像和 codec。生成、写盘及结果校验均不计入耗时。

**这个探针刻意不挂载阅读器，不经过完整 provider 生命周期或 Flutter ImageCache。** `encoded-memory` 表示重用编码字节后再次解码，不是已解码图像缓存命中；本地文件重复读取也不能被称为真实冷磁盘读取。异步首帧等待时间不等于 UI 线程阻塞时间。

## 2026-10-28 宿主结果

Windows x64、Flutter 3.41.4、Dart 3.11.1，`flutter test` 宿主模式。每组五次的中位数，单位 ms：

| 格式／输入 | 本地读取 | 首帧解码等待 | 读取至首帧总耗时 |
|---|---:|---:|---:|
| PNG／本地文件 | 1.77 | 43.17 | 45.26 |
| PNG／编码字节 | 不读取文件 | 43.42 | 43.77 |
| JPEG／本地文件 | 3.12 | 68.30 | 72.09 |
| JPEG／编码字节 | 不读取文件 | 69.00 | 69.77 |

原始 20 组结果见 [JSONL](data/reader_decode_windows_20261028.jsonl)。这组合成 PNG 为 120,499 字节，JPEG 为 2,424,487 字节；二者来自相同像素，但编码内容和压缩特征不同，不能用此表推导所有 JPEG 比 PNG 慢。单张完整 RGBA 像素为 14,400,000 字节，不包括缓存、纹理和其他内存，不能当作进程总内存。

本机合成样本中，字节已在内存仍需要首帧解码等待。它说明“下载完成”不等于“显示无需解码”，但不证明 Android 上发生了 UI 掉帧，也不证明 #125 的根因。不能将宿主测试耗时换算成真实 FPS，或拿它与 Mihon 的设备表现直接比较。

## 下一轮设备验收

1. 记录已收到的荣耀 winRT／Android 16、JPG／PNG 和本地入口对照，只在必要时补充完整版本／构建号与图片处理设置；保留已有文件与配置，不要求清库、清缓存或重新下载整部。
2. 使用合法可控的同一组图片，分别从在线库、完整下载后的离线入口和纯本地导入入口阅读；核实离线场景确实没有退回网络读取。
3. 对分页、连续、瀑布流分别记录首次读取、翻回刚看过的页面和跨章；固定预加载、缩放、图片处理、刷新率与缓存设置，区分编码字节复用和已解码图像命中。
4. 在 Android profile／release 包上记录 UI／raster 帧耗时、图片读取／解码、GC 和峰值内存；性能采样使用 profile 工具，不能将普通 widget 测试时钟当作真实帧统计。避免上传账号、签名地址和完整私人日志。
5. 只有稳定复现并定位后才选择改动；缓存必须有界，不以无限保活、取消资源收尾、默认降低画质或盲目增加并发换取表面改善。加入对应回归后再邀请原设备复测。
