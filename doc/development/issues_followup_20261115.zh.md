## 继续调查的原设备症状

### #139：后续页面未裁剪

按照提出者的压缩文档场景，生成含八张完整左右白边 PNG 的 ZIP，使用真实 ZIP 解包及本地登记，打开瀑布流后从阅读设置启用裁剪，再逐页滚动检查。八页均符合预期裁剪尺寸；另检查预缓存后的延迟入场，源图片不重复加载。

本轮没有修改裁剪算法。现有完整白色列检测、文字保护、动图／预算限制、串行读回、队列上限、缓存与退出收尾继续生效。测试图片不能代表提出者原图的纸色、微小边缘像素、尺寸或编码，因此 [#139](https://github.com/CyrilPeng/Venera-Next/issues/139) 保持调查状态；跟进平台与构建号、未裁页格式／尺寸及重新进入阅读后的表现，以便区分图像条件和生命周期问题。

### #178：缓存反向翻页和松手动画

提出者 RC2 诊断的两组样本为：

| 指标 | 正向 | 反向 |
| --- | ---: | ---: |
| 采集时长 | 24.35 秒 | 12.35 秒 |
| 帧数 | 2,454 | 1,133 |
| 超预算帧 | 42（1.71%） | 55（4.85%） |
| UI P95 | 3.789 毫秒 | 6.900 毫秒 |

反向样本未记录新的来源读取、编解码初始化或首次解码，最大图片显示等待为 104 微秒。应继续排查已有图片的布局与渲染。两组采样时长、翻页频率等条件不同，不能据其比例直接证明反向实现的额外成本。

旧报告 `slowestColumns` 的首列 `receivedAtUs` 是收到批量帧回调的时刻。Flutter Release 通常约一秒批量上报；该列约一秒聚集不足以关联到时钟／电量定时器。本次 schema 2 保留原字段顺序，追加相对采集开始的 `vsyncStartUs` 与 `buildStartUs`，负数标记采集开始前的帧。后续同条件采集可以按真实帧时间继续定位；本轮没有改变状态轮询频率。

正反向半页触摸拖动的回归检查未出现松手立即位置跳变，并最终到达预期页面；该检查不能代替 Android 120 Hz 下的动画速度、渲染与肉眼体验。因此 [#178](https://github.com/CyrilPeng/Venera-Next/issues/178) 保持开放。
